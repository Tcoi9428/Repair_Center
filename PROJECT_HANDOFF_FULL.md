# Ремонтный Центр — полный контекст проекта для продолжения в Codex

Дата актуализации: 24 сентября 2026 года.

Этот файл предназначен для переноса проекта на другое устройство и продолжения разработки без потери принятых решений. Он объединяет исходную бизнес-задачу, решения из чата, текущее состояние кода, правила интерфейса и ближайшие этапы. Ранняя дословная часть диалога сохранена отдельно в `CHAT_HISTORY.md`; подробное исходное техническое задание извлечено в `analysis/requirements-source.md`.

## 1. Бизнес-контекст

Компания занимается ремонтом и техническим обслуживанием горно-шахтной техники:

- погрузочно-доставочные машины грузоподъёмностью 10, 14 и 17 тонн;
- шахтные автосамосвалы грузоподъёмностью 30 и 45 тонн;
- самоходные буровые установки;
- шахтная вспомогательная техника.

Выполняются регламентные работы ТО-250, ТО-500 и другие виды ТО, аварийные и плановые ремонты. Цель — создать собственную цифровую систему управления ремонтами уровня SAP PM / ТОРО с учётом нетиповых процессов сервисной компании.

Система называется **«Ремонтный Центр»**.

## 2. Границы MVP и подход к разработке

Разработка ведётся небольшими функциональными этапами. После каждого этапа бизнес-процесс проверяется пользователем и при необходимости корректируется.

В текущий MVP не входят:

- интеграции со сторонними системами;
- полноценная отчётность и BI-аналитика;
- мобильное приложение;
- сложная отказоустойчивая инфраструктура.

Будущий мобильный этап должен поддерживать работу мобильных бригад, чек-листы ТО, подтверждение операций, QR-коды, фото- и видеофиксацию дефектов, в том числе работу при нестабильной связи.

## 3. Согласованная архитектура

Текущий выбор:

- backend и серверная HTML-часть — Python и Django;
- база данных — PostgreSQL;
- интерфейс — Django templates, HTML, CSS и JavaScript;
- сервер публикации — Ubuntu Server;
- структура приложения — модульный монолит с отделением бизнес-правил от представления.

Flutter не используется в браузерном MVP. Его следует рассмотреть на мобильном этапе. Flutter не заменяет backend: мобильному клиенту всё равно понадобятся Django API, PostgreSQL, авторизация и правила предметной области.

## 4. Визуальный стиль

Согласована палитра:

- синий `#006cb5`;
- графитовый `#1c1e20`;
- белый `#ffffff`.

Выбрана айдентика № 2 «Модуль»: геометрическая монограмма **«РЦ»**. Название во всех материалах и интерфейсе — «Ремонтный Центр».

Интерфейс должен выглядеть как современное рабочее место специалиста:

- без перегрузки элементами;
- без больших бесполезных пустых областей;
- с читаемым шрифтом;
- с понятными новым пользователям подписями, статусами и действиями;
- с иконками меню и тематическими изображениями в карточках.

Основные бренд-файлы находятся в `static/branding/`. В карточке оборудования используется изображение ПДМ в оранжево-чёрной промышленной окраске: `static/branding/equipment-pdm-card-v2-orange.png`.

## 5. Реализованные публичные и служебные экраны

- `/` — публичная стартовая страница с HTTP 200 без обязательной авторизации;
- `/login/` — отдельная тематическая страница входа;
- `/workspace/` — рабочее место пользователя;
- `/nsi/` — раздел нормативно-справочной информации;
- `/admin/` — техническая панель Django.

Публичная страница создана, чтобы домен не выглядел как страница, предназначенная только для авторизации. Страница входа выполнена по мотивам предоставленного пользователем примера, но в теме «Ремонтного Центра».

## 6. Роли и доступ

Реализованы роли:

| Шифр | Наименование |
|---|---|
| `SYS_ADMIN` | Администратор системы |
| `NSI` | Специалист НСИ |
| `PLAN_SPEC` | Специалист по планированию |
| `SITE_HEAD` | Начальник участка |
| `REPAIR_ENG` | Инженер по ремонту оборудования |
| `SUPPLY_SPEC` | Специалист по снабжению |
| `FIN_SPEC` | Специалист по финансам |
| `PLAN_HEAD` | Руководитель планирования |
| `SERVICE_HEAD` | Руководитель сервиса |

Один пользователь может иметь несколько ролей. Итоговые права суммируются. У роли есть постоянный шифр, описание и область действия по экранам и операциям.

Реализованы:

- подача пользователем заявки на роль;
- согласование или отклонение заявки администратором;
- обязательный комментарий при отклонении;
- назначение и отзыв нескольких ролей;
- создание пользователей администратором;
- редактирование прав обычных ролей;
- журнал событий доступа;
- защита от повторного решения и дублирования ожидающих заявок.

Пароли и секреты не хранятся в Git. Локальные реквизиты находятся в `.local/access.txt`, а настройки — в `.env`; оба пути исключены через `.gitignore`.

## 7. Навигация

Левое меню сгруппировано:

- «Моё рабочее место»;
- раскрываемая группа «Справочники»;
- раскрываемая группа «Роли и доступ».

В группе «Справочники» находятся оборудование, предприятия, типы техники, модели техники, признаки техники, признаки гарантийности и статусы техники.

## 8. Реализованные справочники

Через пользовательский интерфейс создаются и редактируются:

1. Предприятия.
2. Типы техники.
3. Модели техники, связанные с типом.
4. Признаки техники.
5. Признаки гарантийности.
6. Статусы техники.
7. Оборудование.

Создание и редактирование справочников доступно ролям `SYS_ADMIN` и `NSI`. Остальные роли могут получать право просмотра через область действия роли.

Для предприятий, типов и моделей техники есть персональные карточки просмотра. Кнопка «Редактировать» видна пользователям с соответствующим правом.

## 9. Справочник предприятий

В коде модель по-прежнему называется `Company`, но пользовательское название раздела — **«Предприятия»**.

Порядок сведений в карточке предприятия:

1. Код предприятия.
2. Наименование предприятия — полное наименование.
3. Основное предприятие — полное наименование основного предприятия.
4. Сокращённое наименование.
5. Город / населённый пункт.
6. Договор на сервисное обслуживание.
7. Номер сервисного договора.
8. Контактный адрес.
9. ФИО руководителя.

Прочие поля с вариантами наименований в карточке не показываются, хотя сохраняются в модели для совместимости с исходными данными.

Из файла `ПКиДП.xlsx` были загружены 16 предприятий. Исходный файл не менялся. MarkItDown не смог обработать файл в окружении, поэтому использован `openpyxl`; результат анализа сохранён в `analysis/pkidp-source.md`.

## 10. Справочник оборудования

Это основной реализованный справочник. Поля и вкладки были сформированы на основе файла «Архитектура справочника оборудования.xlsx».

Карточка содержит:

- фоновое изображение техники;
- полное наименование вида `ПДМ 10 ШААЗ гар.№ 265 зав.№0020` в одну строку;
- идентификатор и статус;
- вкладки «Основное», «Условия гарантии», «Установленные узлы», «Документы»;
- историю изменений;
- кнопку редактирования при наличии права.

Поля внутри каждой вкладки заполняют сначала первый столбец сверху вниз, затем второй столбец сверху вниз.

### Идентификатор оборудования

Формируется автоматически без пробелов и тире:

`код места эксплуатации + числовой ID типа + числовой ID модели + заводской номер из четырёх цифр`.

Перед ID типа и модели нули не добавляются. Пример: `1000110020`.

### Предприятия в карточке

- «Предприятие-собственник» показывает `company_name_top_full`; если оно не заполнено, используется `company_name_full` выбранного собственника.
- «Место эксплуатации» показывает `company_name_full` выбранного предприятия эксплуатации.
- Коды и сокращённые названия в этих двух строках карточки не используются.

### Прочие правила

- Модель должна соответствовать выбранному типу техники.
- Заводской номер нормализуется до четырёх цифр.
- Гарантийные даты рассчитываются по дате ввода, сроку гарантии и продлению.
- Поддерживаются изображение техники, договор поставки машино-комплекта, инструкция и дополнительные документы.
- Для записей ведётся версия и аудит изменений.
- Устаревшая форма не перезаписывает более новую версию записи.

## 11. История и безопасность данных

Для справочников реализованы автор изменения, дата и время, версия записи и значения до/после изменения. Физическое удаление через обычный интерфейс не предусмотрено. Связи используют защиту там, где удаление родительской записи разрушило бы историю.

В репозиторий не должны попадать:

- `.env`;
- `.local/`, включая локальную PostgreSQL и файл паролей;
- загруженные пользователями файлы из `media/`;
- виртуальное окружение `.venv/`;
- собранная статика `staticfiles/`;
- временные базы и логи.

## 13. Локальный запуск

Проверенное локальное окружение — Windows, Python 3.12+ и PostgreSQL.

```powershell
cd C:\Users\i.petrikin\Documents\ChatGPT\RepairCenter
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
# Заполнить уникальный DJANGO_SECRET_KEY и параметры PostgreSQL
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py setup_nsi --seed
.\.venv\Scripts\python.exe manage.py createsuperuser
.\.venv\Scripts\python.exe manage.py runserver
```

Правильный результат запуска:

```text
System check identified no issues (0 silenced).
Starting development server at http://127.0.0.1:8000/
```

Также есть локальный сценарий:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start-local.ps1
```

## 14. Проверки

```powershell
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py test accounts directories maintenance
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
```

Последний подтверждённый правильный результат:


Тесты используют временную PostgreSQL и требуют права `CREATEDB` у тестового пользователя.

## 17. Ближайшее продолжение разработки

Функционал следующих процессов ещё нужно подробно согласовать перед реализацией:

- входящая заявка на ремонт;
- внутренний наряд-заказ;
- утверждение и неизменяемость действующих версий технологических карт;

- дефекты и частичное выполнение;
- состав бригады и фактическое время каждого сотрудника;
- материалы и запасные части;

- QR-код наряд-заказа;
- наработка, простой и показатели надёжности;
- мобильная работа и синхронизация.

Перед кодированием каждого процесса нужно уточнять статусы, переходы, роли, обязательные поля, правила отмены и исправления, а затем реализовывать один завершённый вертикальный сценарий.
