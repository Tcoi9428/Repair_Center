# Ремонтный Центр — MVP, оборудование, справочники и ролевой доступ

Полный контекст решений и инструкция для продолжения разработки на другом устройстве: [PROJECT_HANDOFF_FULL.md](PROJECT_HANDOFF_FULL.md).

## Публичная страница и доступ

`/` — публичная информационная страница, HTTP 200 без перенаправления на авторизацию, также доступна вошедшим пользователям. `/login/` — отдельная страница входа; `/workspace/` — личное рабочее место; `/nsi/` — справочники. После выхода открывается публичная страница. Такая структура отделяет публичную информацию от закрытого приложения, но сама по себе не гарантирует отсутствие блокировок домена.

Страница выполнена в фирменном стиле РЦ. Сайт-пример service-okt.site не ответил при проверке из окружения разработки, поэтому точное визуальное соответствие ему не проверялось.

Страница входа `/login/` оформлена как отдельный защищенный экран: тематический блок с ПДМ в шахтной выработке, карточка авторизации, показ/скрытие пароля, состояние ошибки, справка по доступу и возврат на публичную страницу. На планшете и телефоне блоки перестраиваются вертикально. Оригинальное фоновое изображение хранится в `static/branding/login-hero-v1.png`.

Каждому пользователю доступна подача заявки в «Мои заявки на роли». Укажите роль и обоснование. Администратор открывает «Согласование заявок», проверяет права роли и принимает решение. При согласовании роль добавляется, существующие сохраняются. Отклонение требует комментария; после него можно подать новую заявку. Повторная ожидающая заявка на ту же роль и повторное решение по обработанной заявке запрещены. Собственные заявки администратор не согласовывает.

Администратор системы может создавать учетные записи, предоставлять и отзывать роли с указанием основания, изменять права обычных ролей и смотреть журнал доступа через основной интерфейс. Флаги Django `is_staff` и `is_superuser` для этой роли не требуются. Созданный пользователь первоначально не имеет ролей, но может войти и подать заявку. Публичная самостоятельная регистрация в этот этап не входит. Пароль новой учетной записи передается сотруднику администратором вне системы.

| Шифр | Роль | Начальные права |
|---|---|---|
| SYS_ADMIN | Администратор системы | Все справочники; пользователи, роли, согласование и журнал доступа |
| NSI | Специалист НСИ | Просмотр, создание и редактирование справочников |
| PLAN_SPEC | Специалист по планированию | Просмотр справочников |
| SITE_HEAD | Начальник участка | Просмотр справочников |
| REPAIR_ENG | Инженер по ремонту оборудования | Просмотр справочников |
| SUPPLY_SPEC | Специалист по снабжению | Просмотр справочников |
| FIN_SPEC | Специалист по финансам | Просмотр справочников |
| PLAN_HEAD | Руководитель планирования | Просмотр справочников |
| SERVICE_HEAD | Руководитель сервиса | Просмотр справочников |

Начальные права новых бизнес-ролей — рабочее допущение до уточнения процессов. Экраны планирования, ремонта, снабжения и финансов еще не реализованы. Описание роли отделено от фактических разрешений: последние показаны в раскрываемом списке «Доступные экраны и действия». Права редактируются флажками для существующих справочников и суммируются по всем ролям пользователя. Разделения данных по участкам/предприятиям пока нет: область действия — экраны и операции, как в запросе. Шифры постоянные. Права SYS_ADMIN фиксированы, назначение этой роли возможно только администратором.

Для проверки: войдите как `admin`, создайте пользователя без ролей; войдите им и запросите NSI; под `admin` согласуйте заявку. Ожидаемый результат: до согласования пользователю недоступны справочники, после — видны все шесть и кнопки создания/редактирования. Отзыв NSI закрывает доступ, если его не дает другая роль. Решения и изменения отражаются в журнале.

Существующий `admin` остается техническим суперпользователем с полным доступом вне зависимости от групп. Существующий `nsi` сохраняет свою роль. Управление доступом в обычной работе выполняйте в новом интерфейсе: прямые изменения групп/прав через техническую панель Django обходят прикладной журнал. Техническая панель предназначена для суперпользователя. Собственные роли через новый интерфейс не изменяются — нужен другой администратор.

Рабочий веб-сервис на Django, PostgreSQL и HTML/CSS/JavaScript. Реализованы справочник оборудования, предприятия, типы и модели техники, признаки техники, признаки гарантийности и статусы техники. Фирменная палитра: #006cb5, #1c1e20, #ffffff; используется согласованный логотип РЦ.

## Открыть на этом компьютере

Адрес: http://127.0.0.1:8000/ . Учетные записи и сгенерированные пароли находятся в `.local/access.txt`: `nsi` — специалист НСИ; `admin` — администратор пользователей. Эти пароли предназначены для локальной разработки.

Если сервер остановлен, откройте PowerShell в папке проекта:

```powershell
cd C:\Users\i.petrikin\Documents\ChatGPT\RepairCenter
powershell -ExecutionPolicy Bypass -File .\scripts\start-local.ps1
```

Успешный запуск: `System check identified no issues (0 silenced)` и `Starting development server at http://127.0.0.1:8000/`. Если порт уже занят работающей копией сервиса, откройте указанный адрес. Закрытие окна/Ctrl+C останавливает веб-сервер. Локальный PostgreSQL работает отдельно на 127.0.0.1:55432, файлы базы — `.local/pgdata`. Не удаляйте эту папку: в ней сохраненные данные.

## Что доступно

- Справочник оборудования с поиском и фильтрами по типу и статусу. Строка открывает персональную карточку единицы техники.
- Карточка оборудования с фотографией, полным наименованием вида `ПДМ 10 ШААЗ гар.№ 265 зав.№0020` и вкладками «Основное», «Условия гарантии», «Установленные узлы», «Документы».
- Идентификатор формируется автоматически без разделителей: код места эксплуатации + числовой идентификатор типа + числовой идентификатор модели + четырехзначный заводской номер. Например: `1000110020`.
- Дата окончания и текущий статус гарантии рассчитываются по дате ввода, сроку гарантии и длительности продления. Сроки задаются в днях или месяцах.
- В карточку можно загрузить фотографию, договор поставки машино-комплекта, инструкцию по эксплуатации и несколько дополнительных документов с названиями. Файлы сохраняются в каталоге `media/equipment/`.
- Создание, просмотр и редактирование всех справочников через единый интерфейс.
- Все справочники, включая раздел «Предприятия», собраны в раскрываемую группу левого меню и снабжены понятными пиктограммами. Управление ролями и доступом вынесено в отдельную группу.
- Строка предприятия, типа или модели техники открывает персональную карточку только для просмотра. Кнопка «Редактировать» появляется у администратора и специалиста НСИ; для остальных ролей карточка остается без изменения данных.
- Карточки предприятий и ПДМ используют тематические изображения. ПДМ выполнена в оранжево-чёрной промышленной окраске. Изображения находятся в `static/branding/company-card-v1.png` и `static/branding/equipment-pdm-card-v2-orange.png`.
- Поиск, постраничный список, фильтр моделей по типу, предприятий по наличию договора, статусов по активности.
- Автоматические системные идентификаторы. Код предприятия вводится пользователем и уникален; начальные нули сохраняются.
- Обязательный выбор типа при создании модели. Грузоподъемность необязательна, измеряется в тоннах, до трех знаков после запятой; допускается запись `14,5`.
- Роль «Специалист НСИ» дает просмотр, создание и редактирование справочников. Обычный пользователь без прав получает отказ, в том числе при прямом обращении к URL.
- История: автор, время и сохраненные значения до/после изменения. Последние 10 событий видны в карточке, полные значения — администратору в журнале изменений.
- Защита от перезаписи чужих изменений: если запись сохранена другим пользователем, устаревшая форма не сохраняется.
- У статусов есть признак активности. «Списано» может быть активным значением справочника: активность означает доступность самого статуса.

Физическое удаление записей через интерфейс не предусмотрено. Связанные модели защищены от удаления их типа. Работы, наряд-заказы, оборудование как отдельные единицы, интеграции, аналитика и мобильное приложение относятся к следующим этапам.

## Начальные данные и принятые правила

Из `ПКиДП.xlsx` загружены **16 предприятий**. Также добавлены 4 типа, 4 примера моделей ПДМ, 2 признака техники, 2 признака гарантийности и 2 статуса. Назначения типов являются стартовыми текстами, их можно отредактировать.

Для предприятия обязательны код и полное наименование. Остальные текстовые поля пока необязательны: в исходном файле есть пропуски. Одинаковые сокращенные наименования предприятий допустимы. Основное предприятие хранится в двух текстовых полях, как в запросе, без неоговоренной иерархии связей. Номер договора можно заполнить позднее при выбранном «Да»; при «Нет» непустой номер вызывает ошибку. Пробелы по краям удаляются. Имена типов, признаков и статусов не дублируются без учета регистра; имя модели уникально внутри выбранного типа.

Исходный Excel не изменялся. MarkItDown оказался недоступен в окружении; файл прочитан через openpyxl, извлечение сохранено в `analysis/pkidp-source.md`.

## Управление пользователями

Войдите как `admin` по адресу http://127.0.0.1:8000/admin/ . Создайте пользователя, в разделе «Права доступа» назначьте группу **Специалист НСИ**, оставьте учетную запись активной. Для обычного специалиста не нужны флаги «Статус персонала» и «Статус суперпользователя».

Ожидаемый результат: после входа этому пользователю видны шесть справочников и кнопки создания/редактирования, но недоступно управление пользователями.

## Установка в новом окружении

Нужны Python 3.12+ и PostgreSQL. Создайте виртуальное окружение, установите `requirements.txt`, скопируйте `.env.example` в `.env` и задайте уникальный секрет Django и параметры своей базы. `requirements-lock-windows.txt` фиксирует проверенное локальное окружение Windows, для Ubuntu используйте `requirements.txt` (добавляет Gunicorn).

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py setup_nsi --seed
.\.venv\Scripts\python.exe manage.py createsuperuser
```

Ожидается применение миграций со статусом `OK`, сообщение `Роль «Специалист НСИ» готова` и успешное создание администратора. `--seed` используется для первоначального наполнения; при обычном запуске повторять не нужно. Роль существующему пользователю можно назначить командой `manage.py setup_nsi --username ИМЯ`.

Импорт предприятий для первоначальной загрузки:

```powershell
.\.venv\Scripts\python.exe manage.py import_pkidp "C:\путь\ПКиДП.xlsx" --dry-run
.\.venv\Scripts\python.exe manage.py import_pkidp "C:\путь\ПКиДП.xlsx"
```

Проверочный запуск не сохраняет данные. Повторная загрузка пропускает уже существующие коды, не перезаписывая правки. Ошибка строки отменяет загрузку всего файла. Для приложенного файла в пустой базе результат — 16 созданных предприятий, при повторе — 16 пропущенных.

`scripts/init-local.py` — одноразовая настройка новой локальной базы из заранее распакованных официальных бинарных файлов PostgreSQL в `.local/postgresql/pgsql`; на уже настроенном компьютере повторно не запускать. `scripts/create-local-users.py` — одноразовое создание локальных тестовых учетных записей, существующие пароли не меняет.

## Ubuntu Server

Публикация на сервере пока не выполнялась. Для нее потребуются отдельная PostgreSQL-база и пользователь, виртуальное окружение, миграции, Gunicorn под systemd и Nginx с HTTPS. Задать `DJANGO_DEBUG=False`, рабочий домен в `DJANGO_ALLOWED_HOSTS`, новые секреты, выполнить `collectstatic`. При TLS на обратном прокси отдельно настроить корректную передачу HTTPS-признака только от доверенного прокси. Не использовать `runserver` для публикации.

До рабочей эксплуатации настроить резервное копирование PostgreSQL с проверкой восстановления и ограничить доступ к базе. `.env`, `.local`, пароли и локальная база исключены из Git; их также нельзя включать в общие ZIP-архивы. Существующие исторические материалы проекта не изменялись.
